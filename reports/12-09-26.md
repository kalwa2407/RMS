### 3.2. Workstream 2: PD Coins Loyalty Engine & Financial Guardrails

The PD Coins loyalty program was engineered with non-negotiable financial safeguards to drive repeat customer retention without eroding food cost margins.

#### A. Financial Guardrails Matrix
| Rule | Parameter | Implementation & Rationale |
|---|---|---|
| **Conversion Rate** | 1 PD Coin = ₹1.00 Discount | Simple, transparent 1:1 conversion rate understood immediately by customers. |
| **Minimum Order Threshold** | ₹300 Subtotal | Prevents virtual currency redemption on low-ticket convenience orders (beverages, plain breads). |
| **Maximum Burn Cap** | 25% of Bill Subtotal | Caps restaurant discount liability at 25% of food value. A customer with 1,000 coins ordering ₹800 can redeem at most 200 coins. |
| **Net Paid Re-Earning** | 10% on `(Subtotal - Discount)` | Eliminates "double-dipping" — customers only earn cashback on the portion of the bill they actually pay for. |
| **Auto-Expiry Policy** | 45 Days from Earning Date | Creates genuine visit urgency and prevents unbounded loyalty debt accrual on restaurant balance sheets. |

#### B. 45-Day Expiry Implementation (`backend/server.py`)
```python
def apply_coin_expiry(customer: dict) -> dict:
    EXPIRY_DAYS = 45
    now = get_ist_now()
    history = customer.get("coins_history", [])
    newly_expired = 0
    updated_history = []

    for entry in history:
        if entry.get("type") == "earned" and not entry.get("expired"):
            earned_at = parse_iso(entry.get("timestamp"))
            if (now - earned_at).days >= EXPIRY_DAYS:
                newly_expired += entry.get("coins", 0)
                updated_history.append({**entry, "expired": True})
                continue
        updated_history.append(entry)

    if newly_expired > 0:
        updated_history.append({
            "type": "expired",
            "coins": newly_expired,
            "balance_after": max(0, customer.get("pd_coins", 0) - newly_expired),
            "note": f"{newly_expired} coins auto-expired (45-day policy)",
            "timestamp": now.isoformat(),
        })
        customer["pd_coins"] = max(0, customer.get("pd_coins", 0) - newly_expired)
        customer["coins_history"] = updated_history

    return customer
```

## 4. Defect Tracking & Known Issues

During quality assurance and user testing today, two defects were logged:

### DEFECT-12-09-01: PD Coins Not Deducted from Customer Balance on Online Order
* **Severity:** High (Major Feature Broken) | **Priority:** P1
* **Component:** `backend/server.py` (`POST /api/orders`) & `CustomerAuthContext.jsx`
* **Symptom:**
  When a customer applies PD Coins during an online order, the bill discount is calculated correctly on the order summary, but the customer's wallet balance on the Customer Dashboard remains unchanged (e.g. remains at 600 coins), and no deduction or cashback transaction appears in the Rewards tab.
* **Root Cause:**
  In `backend/server.py`, the redemption block is guarded by:
  ```python
  if requested_coins > 0 and optional_customer:
      uid = optional_customer["uid"]
  ```
  If `optional_customer` returns `None` (due to Firebase auth Bearer token expiration, missing header in intermediate fetch, or guest fallback), the server silently bypasses wallet deduction even though `order.coins_to_redeem` and `customer_uid` were present in the payload.
* **Resolution Status:**
  Resolved.
  1. Decoupled wallet debit from `optional_customer` in `backend/server.py` (`POST /api/orders`): Resolves customer identity through token UID, request payload `customer_uid`, 10-digit phone number, or email fallback.
  2. Fixed `refreshProfile` in `CustomerAuthContext.jsx` to be an async function that force-refreshes the Firebase token (`user.getIdToken(true)`) and fetches the latest profile.
  3. Updated `CustomerDashboard.jsx` and `Order.jsx` to proactively acquire fresh tokens and await `refreshProfile()` upon order placement, updating wallet balances and transaction history immediately.
